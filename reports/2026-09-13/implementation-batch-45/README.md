# الدفعة 45: مسار إصدار دائم وموقّع

## ما أُضيف

- تشغيل `Desktop Release Build` عند tags التي تبدأ بـ`v` مع اشتراط تطابق tag مع نسخة `pubspec.yaml` الكاملة.
- رفض tag خفيف أو commit غير موجود في تاريخ `origin/main`.
- توقيع تطبيق Windows قبل إدخاله في NSIS، ثم توقيع المُثبّت النهائي.
- تحقق Authenticode من حالة التوقيع وبصمة شهادة الموقّع، واشتراط شهادة ختم وقت عند الإصدار الحقيقي.
- إنشاء `SHA256SUMS` وحساب بصمتي مُثبّت Windows وحزمة Debian والتحقق منهما.
- إنشاء Draft GitHub Release بعد نجاح الاختبارات والبناء ودورة التثبيت، دون نشره للعامة.
- إلغاء runs القديمة لنفس الفرع عند وجود commit أحدث، مع حماية runs الخاصة بالـtags من الإلغاء.

## اختبار التوقيع دون أسرار إنتاج

ينشئ Windows runner شهادة Code Signing مؤقتة داخل الذاكرة، يصدرها كـPFX مؤقت، يوقّع نسخة من EXE الحقيقي عبر نفس `sign_windows_release.ps1`، ثم يتحقق من التوقيع وبصمة الشهادة ويحذف الملفات المؤقتة. لا تدخل شهادة الاختبار في حزم المستخدم.

المحاولات الأولى التي استوردت الشهادة إلى Windows Certificate Store علقت حتى مهلة خمس دقائق. استُبدل هذا المسار بتوقيع مباشر عبر `/f` و`/p` من PFX مؤقت دون تعديل مخازن الشهادات؛ انتهى الاختبار الناجح في ثانية واحدة.

## حدود الإثبات

لم تُرفع شهادة ناشر حقيقية إلى Secrets، ولم يُنشأ tag أو Draft Release. لذلك لا يثبت هذا التشغيل نجاح ختم الوقت الخارجي أو سمعة SmartScreen أو صحة اسم الناشر التجاري أو مسار النشر النهائي. يلزم تنفيذ `RELEASE_PROCESS_AR.md` بعد اعتماد شهادة الناشر، ثم اختبار ملفات المسودة نفسها على أجهزة Windows وLinux الفعلية وتوثيق `FIELD_ACCEPTANCE_AR.md` قبل النشر العام.
