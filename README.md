# ALIkhlasPOS v2

تطبيق Flutter Desktop لإدارة محل واحد أوفلاين. المسار النشط الآن هو v2 داخل:

`Frontend/alikhlas_pos`

`Frontend/alikhlas_pos/lib/main.dart` يشغل `ALIkhlasV2App` مباشرة. لا يحتاج التطبيق إلى Backend أو Docker أو PostgreSQL أو Redis في وقت التشغيل.

## المعمارية الحالية

- Flutter Desktop + Riverpod.
- SQLite عبر drift.
- واجهة Apple/iOS-inspired Liquid Glass مبنية على Flutter Material مع أصول محلية.
- خط الواجهة العربي هو Cairo bundled داخل التطبيق ويعمل أوفلاين.
- ملفات PDF تستخدم Cairo المحلي من أصول التطبيق، بدون تحميل Google Fonts وقت الطباعة.
- قاعدة البيانات الافتراضية: `alikhlas_v2.db` داخل مسار بيانات التطبيق الذي يرجعه `path_provider`.
- كل العمليات المالية تمر عبر use-cases في `Frontend/alikhlas_pos/lib/v2/application/v2_use_cases.dart`.
- الدفتر `LedgerEntry` و`LedgerLine` هو مصدر الحقيقة للأرصدة والتقارير.
- القيم المالية محفوظة كـ integer minor units، وليست `double`.

## التشغيل

```bash
cd Frontend/alikhlas_pos
flutter pub get
flutter run -d linux
```

في أول تشغيل لقاعدة جديدة، تظهر شاشة قصيرة لكتابة اسم المحل وإنشاء حساب المالك: الاسم وكلمة مرور يختارها صاحب المحل ويؤكدها. لا توجد كلمة مرور افتراضية منشورة أو قابلة للتخمين. قاعدة بيانات موجودة مسبقًا تحتفظ بحساباتها الحالية؛ لا يغيّر هذا الإعداد كلمات المرور أو بيانات المحل أثناء الترقية.

بعد إنشاء المالك، يعرض التطبيق رمز استعادة خاصًا بالمحل مرة واحدة. يجب حفظه خارج الجهاز أو طباعته؛ عند نسيان كلمة المرور يُدخل الرمز لاختيار كلمة مرور جديدة، ثم يصدر التطبيق رمزًا بديلًا ويلغي السابق. بعد خمس محاولات خاطئة تتوقف الاستعادة 15 دقيقة. لا توجد كلمة مرور دعم عامة، ولا يمكن استعادة قاعدة قديمة لم يُنشأ لها رمز إلا وفق إجراء الدعم المعتمد.

## Checklist تشغيل يدوي سريع

بعد أي build مهم، نفذ المسار التالي على قاعدة اختبار:

1. افتح التطبيق، وأنشئ حساب المالك إن كانت هذه أول قاعدة للمحل، ثم سجل الدخول.
2. افتح وردية برصيد افتتاحي.
3. أضف منتجًا أو نفذ شراءً لزيادة المخزون.
4. نفذ بيعًا من شاشة POS، ثم جرّب تحصيل قسط أو سداد مورد عند وجود خطة.
5. افتح كشف حساب عميل أو مورد وجرّب طباعة PDF.
6. نفذ مرتجعًا مرتبطًا بفاتورة بيع.
7. أنشئ نسخة احتياطية من شاشة النسخ.
8. أغلق الوردية وتأكد أن الفرق واضح.

## الواجهة والخط

- الواجهة تستخدم اتجاه Apple/iOS-inspired Liquid Glass: ألواح شفافة، حواف مضيئة، وخلفية هادئة غير مسطحة.
- الخلفية مرسومة بالكود بطبقات ضوء ناعمة لإظهار الزجاج بدون صور أو أصول ثقيلة.
- blur الحقيقي محدود ومركزي للألواح الكبيرة؛ الحقول والقوائم والأزرار تستخدم glass-like styling بدون `BackdropFilter`.
- الخط العربي `Cairo` مدمج محليًا داخل `Frontend/alikhlas_pos/assets/fonts`.
- الأوزان المدمجة: 400، 500، 600، 700 فقط.
- ترخيص الخط مرفق في `Frontend/alikhlas_pos/assets/fonts/OFL.txt`.
- التطبيق لا يعتمد على `google_fonts` في وقت التشغيل.
- صور المنتجات والخلفيات المختارة تُنسخ إلى مسار بيانات التطبيق داخل `product-images/` و`backgrounds/` حتى لا تختفي عند نقل الملف الأصلي.
- أبعاد ملصق الباركود قابلة للتعديل من شاشة الإعدادات، والافتراضي `40 × 30 mm`.
- يمكن طباعة باركود الوارد بعد تسجيل فاتورة الشراء، أو إعادة طباعة باركود منتج موجود من شاشة المخزون عند تلف الملصق القديم.

## الاختبار والبناء

ملف التسليم العملي موجود في `DELIVERY_HANDOFF.md` ويحتوي على commit البناء، روابط الحزم، وchecklist الاختبار اليدوي قبل التسليم النهائي. إجراء إنشاء Release دائم وموقّع موثق في `RELEASE_PROCESS_AR.md`.

```bash
cd Frontend/alikhlas_pos
dart analyze lib/v2 lib/main.dart test/v2
flutter test
HOME=/tmp PUB_CACHE=/home/el3laimy/.pub-cache /home/el3laimy/development/flutter/bin/flutter build linux
```

أمر Linux build الأخير مستخدم في هذه البيئة لأن Flutter SDK موجود في `/home/el3laimy/development/flutter`.

لبناء Windows أو Linux من GitHub، استخدم GitHub Actions workflow باسم `Desktop Release Build`. يعمل على pull requests والتحديثات إلى `main` أو فروع `codex/**`، ويرفع bundle لكل نظام، وحزمة تثبيت Debian باسم `alikhlas-pos-linux-deb` ومُثبّت Windows باسم `alikhlas-pos-windows-installer`.

الأمر المحلي من Windows:

```bash
cd Frontend/alikhlas_pos
flutter build windows
```

يبني CI مُثبّت Windows رسوميًا لكل مستخدم في `%LOCALAPPDATA%\Programs\ALIkhlas POS`، ويضيف اختصارات قائمة Start وسطح المكتب، ولا يحذف بيانات المحل عند إزالة التطبيق. اجتازت الحزمة الآلية التثبيت والترقية والإزالة وإعادة التثبيت وبقاء البيانات على Windows runner. تبقى builds العادية غير موقّعة؛ أما tag الإصدار فيُرفض إذا لم تتوفر شهادة الناشر، ويوقّع التطبيق والمُثبّت ويتحقق منهما قبل إنشاء Draft Release. لا يُنشر الإصدار للمستخدم النهائي قبل قبول جهاز Windows الفعلي وفحص SmartScreen.

لـ Debian/Ubuntu ‏x64، يمكن تجهيز حزمة تثبيت محلية بعد بناء Linux:

```bash
cd Frontend/alikhlas_pos
bash tool/build_linux_deb.sh build/linux/x64/release/bundle build/linux/x64/release/package 1.1.0
bash tool/verify_linux_deb.sh build/linux/x64/release/package/alikhlas-pos_1.1.0_amd64.deb
sudo apt install ./build/linux/x64/release/package/alikhlas-pos_1.1.0_amd64.deb
```

يتحقق الفحص من بنية الحزمة وملف التشغيل وملف سطح المكتب والمكتبات ومن حل الاعتمادات عبر APT، مع دعم اسم GTK في Debian/Ubuntu الأقدم وUbuntu 24.04. اجتازت الحزمة دورة التثبيت والترقية والإزالة وإعادة التثبيت على GitHub runner نظيف، وترفعها CI باسم artifact مستقل `alikhlas-pos-linux-deb`. يبقى قبولها على جهاز Ubuntu/Debian الفعلي المحدد للتسليم شرطًا قبل اعتمادها للمستخدم النهائي.

## حماية تشغيل البيانات

يمسك التطبيق قفل عملية قبل فتح قاعدة المحل أو التعافي من استرجاع سابق. تشغيل نسخة ثانية على نفس مسار البيانات يُرفض برسالة واضحة. يستمر القفل أثناء الاسترجاع ويتحرر بانتهاء العملية؛ لا تحذف ملف `alikhlas.instance.lock` يدويًا. يجتاز اختبار العمليات الفعلي في CI على Linux وWindows، وتبقى إعادة التجربة على جهازي التسليم ضمن القبول الميداني.

## مسودات فواتير البيع والشراء

- يمكن حفظ فاتورة البيع أو الشراء كمسودة والعودة إليها بعد تسجيل الخروج أو إعادة فتح التطبيق. تحفظ المسودة الكميات والأسعار وقيم الدفع والتقسيط ولا تسجل قيدًا أو حركة مخزون.
- إذا غادر المستخدم شاشة فاتورة معدلة قبل حفظها يظهر تحذير عند التنقل أو تسجيل الخروج أو إغلاق نافذة سطح المكتب. الحفظ يدوي، لذلك يجب ضغط «حفظ مسودة» لحماية التعديلات من توقف الجهاز المفاجئ.
- عند تسجيل الفاتورة تتحول المسودة أولًا إلى طلب معلق دائم، ثم تستخدم حماية معرّف العملية لمنع التسجيل مرتين. الطلب الذي لم ينفذ يمكن إعادته إلى مسودة، أما الطلب الذي له إيصال حفظ فيبقى في مسار التحقق بدل إعادة التنفيذ.
- إذا تعذر قراءة مسودة تالفة تبقى الشاشة قابلة للاستخدام ويظهر خيار لمسح المسودة. يلزم اختبار سلوك إغلاق النافذة على Windows وLinux فعليين قبل اعتماد هذا المسار ميدانيًا.

## النسخ الاحتياطي

- شاشة النسخ الاحتياطي داخل v2 تسمح باختيار مجلد النسخ.
- في أول تشغيل لمحل جديد، يمكن للمالك اختيار مجلد النسخ كخطوة اختيارية؛ بعد إنشاء الحساب يحاول التطبيق إنشاء أول نسخة ويعرض نتيجتها مع رمز الاستعادة. يمكن تخطي الخطوة وضبط الوجهة لاحقًا من شاشة النسخ.
- النسخ اليدوي يستخدم `VACUUM INTO`.
- النسخ التلقائي يعمل عند بدء التشغيل ثم كل 30 دقيقة أثناء بقاء التطبيق مفتوحًا عند وجود مجلد محفوظ. يُفحص الاستحقاق كل دقيقة، ويعاد المحاولة عند فشل الوجهة. وقت آخر نجاح محفوظ في القاعدة لمنع النسخ المتكرر عند إعادة التشغيل.
- الاحتفاظ الافتراضي: آخر 30 نسخة باسم يبدأ بـ `alikhlas-v2-`.
- الاسترجاع يفحص سلامة الملف والجداول والأعمدة والعلاقات قبل إغلاق قاعدة التشغيل، ثم يعيد فحص الملف المنسوخ. يقبل حاليًا نفس إصدار مخطط البيانات فقط؛ دعم استرجاع المخططات الأقدم لم يكتمل بعد.
- يحتفظ الاسترجاع بنسخة رجوع بجوار قاعدة التشغيل باسم ينتهي بـ`.restore-rollback.db`، وعلامة `.restore-pending` أثناء الاستبدال. عند توقف الاسترجاع تُفحص بصمة نسخة الرجوع وسلامتها وتُعاد قبل فتح اتصال التشغيل التالي. النسخة لا تدخل ضمن تدوير آخر 30 نسخة، ويستبدلها الاسترجاع التالي بعد فحص ملفه المرشح. توجد محاكاة اختبار لحالات الانقطاع؛ اختبار قطع الطاقة الفعلي ما زال مطلوبًا.
- فشل النسخ التلقائي بسبب وجهة غير متاحة أو خطأ SQLite لا يمنع تسجيل الدخول؛ يظهر تنبيه مع رابط لإعداد النسخ.
- يمكن إنشاء حزمة نقل يدوية ZIP تشمل قاعدة البيانات وصور المنتجات والخلفية؛ يفحص الاسترجاع البصمات والمسارات قبل استبدال قاعدة الجهاز. النسخ التلقائي يظل نسخة قاعدة بيانات سريعة ولا يتضمن الصور حاليًا.
- تقدم الإصلاحات والأدلة والمهام المتبقية موثق في `IMPLEMENTATION_PROGRESS_AR.md`.

## المساعدة والدعم

- زر «المساعدة» داخل التطبيق يوضح طريقة التحقق من عملية غير مؤكدة، وأخذ نسخة قبل الاسترجاع، وإعادة طباعة فاتورة حُفظت بالفعل.
- تعرض الشاشة إصدار النسخة المثبتة وتاريخ آخر نسخة تلقائية ناجحة. غياب مجلد النسخ يظهر تحذيرًا حتى قبل موعد النسخة التالية، ويعاد فحصه كل دقيقة أثناء تشغيل التطبيق.
- يمكن معاينة تقرير دعم نصي ثم اختيار مكان حفظه. يتضمن الإصدار والنظام وإصدار مخطط البيانات وحالة النسخ؛ لا يضم قاعدة البيانات أو الفواتير أو بيانات العملاء أو كلمات المرور أو مسارات الملفات، ولا يُرسل تلقائيًا.
- زر «اختبار الطابعة» يجهز صفحة عربية بحجم A4. يجب تجربة الإيصالات والباركود بالحجم الفعلي على الطابعة المستخدمة أيضًا؛ رجوع طلب الطباعة بنجاح لا يؤكد خروج الورق.
- نافذة اختيار مكان الحفظ ومشاركة التقرير تحتاج اختبارًا فعليًا على Windows وLinux قبل التسليم.

## المرتجعات وتكلفة المخزون

- مرتجع البيع ومرتجع الشراء مرتبطان دائمًا بفاتورتهما الأصلية، ويمكن إرجاع كمية جزئية من السطر.
- مرتجع الكاش يحتاج وردية مفتوحة.
- مرتجع التقسيط يقفل ذمة العميل حتى الرصيد المتبقي فقط، وأي فائض يرد كاش أو محفظة.
- تكلفة مرتجع البيع تعكس التخصيص التاريخي الدقيق في `SaleItem.costMinor` وتعيد احتساب أساس قيمة المخزون، فلا تختلط تكلفة البيع القديمة بمتوسط تكلفة شراء لاحق.
- مرتجع الشراء يمنع تجاوز كمية الشراء أو المخزون المتاح، ويخفض ذمة المورد حتى المتبقي فقط؛ فائض ائتمان المورد يُستلم كاش أو محفظة.
- يحتفظ مرتجع الشراء بتكلفة المورد الأصلية، ويخفض المخزون بمتوسط التكلفة الحالي؛ الفرق بين القيمتين يُسجل في حساب فروق المخزون كي يظل الدفتر وتقييم المخزون متزنين.
- فائدة التقسيط لا تُرد تلقائيًا عند المرتجع؛ أي رد للفائدة يحتاج تسوية يدوية منفصلة لاحقًا.
- كشف الحساب يعرض حالة الفاتورة الحالية: الإجمالي، الخصم، الفائدة، المرتجعات، المدفوع، والمتبقي الحالي.

## الجرد وتسوية المخزون

- من قائمة إجراءات الصنف يمكن فتح «جرد وتسوية الرصيد»، ثم إدخال إجمالي الموجود فعليًا واختيار سبب ومراجعة الفرق قبل الاعتماد.
- تُقيّم التسوية بمتوسط التكلفة المحفوظ. الصنف الذي لا يملك تكلفة يطلب تكلفة وحدة قبل المتابعة.
- تحفظ العملية مستندًا وحركة مخزون وقيدًا متزنًا وإيصال منع تكرار داخل معاملة واحدة. إذا تغير الرصيد أو التكلفة أثناء المراجعة يطلب التطبيق تحديث الشاشة وإعادة العد.
- فروق الجرد تظهر في ملخصات اليوم والفترة وتؤثر في الربح. مستند التسوية لا يُحذف لتصحيح التاريخ بصمت.
- من الإعدادات يستطيع صاحب المحل إدخال رصيد افتتاحي للعميل أو المورد أو الخزينة أو المحفظة، ثم مراجعته قبل الاعتماد. تنشئ ذمم العميل والمورد قسطًا واحدًا قابلًا للتحصيل أو السداد، ولا تضيف أرصدة الخزينة والمحفظة مبلغًا وهميًا إلى درج الوردية.

## التصحيحات المالية

- من الإعدادات يستطيع صاحب المحل تسجيل «تصحيح خزينة أو محفظة» فقط عند ظهور فرق بعد عدّ فعلي، مع اختيار زيادة أو عجز وسبب إلزامي ومراجعة قبل الاعتماد.
- التصحيح ينشئ مستندًا مستقلًا وقيدًا متزنًا بين الحساب السائل وحساب فروق مالية موثقة؛ يظهر أثره في الربح وتقارير اليوم والفترة وPDF التقرير.
- تصحيح الخزينة يحتاج وردية مفتوحة، والعملية التي تجعل الخزينة أو المحفظة سالبة تطلب اعتمادًا صريحًا من صاحب المحل.
- لا يمكن استخدامه لتعديل فاتورة بيع أو شراء أو مخزون أو رصيد عميل أو مورد. هذه العمليات تبقى مرتبطة بمستنداتها المتخصصة.
- حفظ الطلب المعلّق وإيصال منع التكرار يعملان مع التصحيح، لذلك لا تؤدي إعادة المحاولة بعد انقطاع التطبيق إلى قيد ثانٍ.

يدعم التطبيق استيراد CSV آمنًا للأصناف والمخزون الافتتاحي: يعرض معاينة وأخطاء كل صف قبل الحفظ، ثم يسجل الدفعة المعتمدة ذريًا مع حماية من تكرار العملية عند إعادة المحاولة.
